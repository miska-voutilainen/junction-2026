# Kickoff

Run once, by Miska (GitHub `miska-voutilainen`), at the start of the event, in a session set to `/model opus` and `/effort max` (or `high` if `/usage` shows the weekly limit already well used) (the skill's own `model` and `effort` last only for the turn it starts in, and kickoff spans several). Think hardest where it decides: the idea check, the stack, the lanes and the spec. Specs for the harness are in `docs/setup.md`; follow them exactly. Gather everything you need in one round of questions, then work without asking until step 6.

**Writes under `.claude/` always ask your user**, even in `acceptEdits` mode: Claude Code protects that folder. Tell your user up front to approve them in steps 1 and 9; a rehearsal without anyone to approve left `settings.json` unwritten.

**Timebox: 90 minutes.** A rehearsal on a realistic brief took 11.5 minutes up to the sign-off (critic, research, a 300-line spec, two cold-read rounds that raised and answered 59 questions). Targets: skeleton PR merged ~45 minutes in, harness core ~75 minutes in. The agent's own work is about 35-60 minutes; the rest is waiting on people (the question round, reading the spec) and the network, so answer fast and read the spec while the issues are created. The rest of the team waits only for the skeleton PR (step 8); everything after it runs while the lanes build. Keep kickoff small: anything that can be a task in a lane is one.

1. **Preconditions and starter settings.** Issue #1 exists, is titled `Agent sync log` and is pinned; the labels from setup.md section 2 exist; `main` has the agent-environment commit (setup.md section 2, step 3); `LANE` is set; you're on a new branch (`chore/kickoff`), not `main`. If any is missing, stop and say which. Then write `.claude/settings.json` from the example in setup.md section 3 with the stack's package manager, without the `hooks` key yet, so the rest of kickoff and the lanes' first hour run without permission prompts.
2. **Gather** from the project info your user gives you, and ask in one message for whatever is missing: the challenge text and judging criteria, the product idea, the demo path, constraints on the stack (anything the challenge requires or rules out; hosting accounts the team already has), the visual direction, the lanes (name, owner, responsibility; the team is Miska `miska-voutilainen`, Elias `eliasnorta` and Veijo `Kasanen`), the feature-freeze and submission times (clock times, from checklist.md's time plan), which plan each person is on (Max 5x or Pro; it decides their model mode and who gets the heaviest lane).
3. **Idea check and research, in parallel:** `product-critic` on the idea and the challenge text; `researcher` on each partner API or SDK the idea depends on, and on the current versions and known problems of the stack candidates. Present the critic's top three to your user with your recommendation; apply what they accept.
   3b. **Choose the stack yourself** (your user leaves it to you). Compare two or three candidates against, in this order: (1) the partner's SDKs and APIs work first-class in it; (2) the demo path runs reliably and fast on a phone, with streaming for the AI; (3) preview deploys per PR on a host the team can use; (4) agents build it well: mainstream, well documented, typed, with an official scaffold CLI; (5) everything in it is free or within the team's credits. Prefer the boring, proven option unless the challenge rewards something specific. Pick one, with the component library, package manager, model ids and host, and write the comparison into `docs/decisions.md` (chosen, rejected and why). It's part of the sign-off in step 6. Then scaffold it yourself with the stack's official CLI (setup.md section 2, step 4; an install, so your user approves the prompt) and commit the generated files on your branch before step 5.
4. **File tree and lanes.** Design the code layout from the stack's official conventions and write it into `CLAUDE.md`'s File tree. Assign every code path to exactly one lane or Shared in the Lanes table. **Lane weights:** Miska takes the heaviest lane, the one on the critical path of the demo (the only Max 5x account; also runs kickoff, so its first feature task should start after T00); Elias (Pro) the second; Veijo (Pro) the lightest. Size the Pro lanes' tasks so a Sonnet session at medium effort can build them: well-specified, no open design questions. Say in the sign-off which lane you judged heaviest and why. Shared: contracts, design tokens, root configs, the package manifest and lockfile, `docs/spec.md`, `.github/`, `.claude/`. Open to all lanes: `README.md`, `CLAUDE.md`, `AGENTS.md`, `docs/` (except `docs/spec.md`). Your backup is Elias (`eliasnorta`, admin on the repo).
5. **Write `docs/spec.md`** from its template, section by section, using the research for exact API shapes. Work plan, in this order:
   - **T00 Agent harness core**, your lane: what step 9 builds (setup.md sections 3-4: lane map, lane module, guard, briefing, their tests). Kickoff builds it itself; it's an issue so other tasks can depend on it (the CI task does, for the lane check).
   - **Foundation tasks (T01…)**, one or two per lane by fit, each its own PR with testable acceptance criteria: design system (component library, tokens file, layout shell, skeleton, empty-state, error-state and toast components); `format-on-edit` and `quality-on-stop` hooks with the lint config (setup.md 4.3-4.4); test harnesses (unit runner, Playwright e2e at 375 px and 1440 px failing on console errors, the screenshot command into `.review/`, `evals/` and the AI client module per `ai-features.md` if a model is used); CI (setup.md 6); the deployed skeleton with preview deploys per PR (production URL into `CLAUDE.md` and the README); docs (`architecture`, `development`, `api`, the stack, model, lanes and design decisions in `decisions`, README pitch and how to run). Each foundation task lists its **pre-agreed shared paths** (e.g. lint and TypeScript configs, `playwright.config`, the tokens file, `.claude/hooks/<file>`, `.claude/settings.json`, `.github/workflows/`); the sign-off in step 6 is the owners' agreement for exactly those.
   - **Contracts and mocks**, so every lane can build against them at once.
   - **Features** along the demo path. Each task one PR, one lane, sized at about 1-3 hours of agent work (the template's sizing note); balance the lanes so each has work the moment the skeleton PR merges.

   Then:
   - **Cold-read check:** give `builder` (sonnet) the spec and three tasks from different lanes, and ask it, without building anything, to list every question it would need answered to build them. Fix the spec until the list is empty. Repeat once with three other tasks.
   - Tick the Ready checklist honestly.

6. **Sign-off.** Show your user, in one message: the stack you chose and why (one line per rejected option), the file tree, the lanes, the demo path and the work plan (IDs, lanes, titles). On their yes, set `Status: ready`. This is the last question of kickoff.
7. **Task issues:** one per work-plan row, title `T<nn> <title>`, labels `task` and `lane:<lane>` (plus `cross-lane` for a task with pre-agreed shared paths), body (via `--body-file`, first line `[agent:<your lane>]`): the spec sections it implements, "Depends on: #a, #b", "Pre-agreed shared paths: …" where there are any, the acceptance criteria as a checklist. Create them in ID order (T00 first) and assign T00 to yourself.
8. **Skeleton PR.** Install every dependency the spec names now, in one lockfile change, so lanes don't fight over the lockfile later. Extend `.gitignore` with the stack's build output and test reports. If a model is used, add `paths:` frontmatter to `.claude/rules/ai-features.md` with the AI client, prompts and evals folders from the File tree, so it loads only when an agent works there (the design and testing rules already work this way). Fill the `CLAUDE.md` placeholders and Commands: run each command that already works once; mark the ones a foundation task sets up with its ID (`# T03`). Ship through `ship-pr` as tier S (`chore: add spec, work plan and project skeleton`): the spec was signed off and the rest is generated scaffold, starter settings and config. The size limit doesn't apply to generated files and lockfiles. There is no CI yet, so merge when the local checks pass. Then tell your user, for the team: `git pull` (or clone), say "join" if they haven't yet or joined before lanes existed, restart Claude Code, say "go"; until the harness core merges, the agents follow the guard's rules by hand (`AGENTS.md`) and open PRs but don't merge them.
9. **Harness core**, from setup.md sections 3-4: the `hooks` key in `.claude/settings.json` (exec form, as in the example), `.claude/lanes.json` (shape and matching order as in the example), the shared lane module, `guard.mjs`, `session-brief.mjs`, and the section 4.6 tests. Use `builder`s in parallel on different files; you write the briefs (point each at setup.md 4.2's implementation notes, which a dry run validated) and verify. Run the tests and setup.md 4.7 steps 1-5 yourself. `tidy` on the whole tree finds nothing. Ship through `ship-pr` as **tier L** (`chore: add agent harness core`, `Closes #<T00>`) and merge.
10. **Timebox check.** If at 90 minutes the harness core isn't green, ship what passes in this order (guard with its tests, then the lane module and `lanes.json`, then the briefing), file the rest as a task for your own lane, and move on. The lanes keep following the rules by hand until then.
11. **Hand off:** `handover` (the first summary on #1). Tell your user to set `/effort medium` now: `max` was for kickoff only (`delegation.md`, Usage guardrails). Its **For other lanes** line says: the harness core is merged; `git merge origin/main`, start a new session, run setup.md section 4.7 (steps 6-7 once their foundation tasks merge), merge `origin/main` into each held PR and merge it when green, then "go".
